# Taste
- Runs projects documentation-first: keeps a structured `docs/` tree (project overview, roadmap, decisions log, progress tracker, per-phase guides) and expects the agent to read the docs before touching code or proposing work. Confidence: 0.65
- On learning projects, prefers to write the implementation personally while the agent explains, proposes bounded tasks, and reviews — the agent should not scaffold or implement unless explicitly asked. Confidence: 0.65
- Even when asking the agent to "help fix" something (e.g. dependency issues), expects the agent to hand back the exact edits for them to apply personally — precise instructions with file location and before/after code blocks — rather than editing files itself; wants to be asked/confirmed first and will push back if the agent starts doing the work ("let me fix that, not go and do it"). Confidence: 0.7
- Comfortable explicitly delegating build/dependency/config plumbing to the agent (e.g. asking it to "fix dependency issues" directly), so the agent may edit build files like `pom.xml` when asked — this is a distinct carve-out from feature implementation, which stays personal. Confidence: 0.4
- Prefers gated progression: open design questions (e.g. versions, auth mechanism, module layout) stay open until their phase, and findings/decisions are resolved before advancing to the next phase. Confidence: 0.55
- Keeps decisions and progress in explicit dedicated docs (`decisions.md`, `progress.md`) as a running record rather than only in chat, and will explicitly ask the agent to update them at checkpoints. Confidence: 0.6
- Treats automated tests as part of the deliverable for any new feature/API, not an optional follow-up. Confidence: 0.5
- Not test-first: writes the implementation first, has the agent review the code until it is "good", and only then adds the tests ("i will add tests once code it good") — so reviews at this stage should judge the production code, not penalize missing tests. Confidence: 0.55
- Works in a Java/Spring Boot + PostgreSQL backend stack (organized under a Java-Stack directory). Confidence: 0.6
- Builds Java/Spring Boot projects with Maven rather than Gradle. Confidence: 0.5
- Picks current LTS Java (e.g. Java 25) with the latest stable supported Spring Boot line, avoiding EOL or non-LTS releases. Confidence: 0.5
- Terse communicator: gives short directives and expects the agent to surface the concrete decisions/options needed to proceed rather than waiting for detailed instructions. Confidence: 0.45
- Works on Windows and prefers to run commands in PowerShell, so instructions should be given in PowerShell form (and tool availability like `winget` confirmed rather than assumed). Confidence: 0.45
- Executes commands literally (copy-pastes them verbatim, including placeholder values like `jdk-25.x.x-hotspot`), so instructions should be exact and runnable: real paths/values, no placeholders, and include the working directory (e.g. an explicit `cd`) rather than relying on the user's current location. Confidence: 0.55
- Learns by asking conceptual "what/why" questions mid-task (e.g. what a Spring bean is, Spring Framework vs Spring Boot, how a mock-stubbed test differs from one using real values, what config profiles are, what flush/clear do) and expects plain-language explanations anchored to their own code and current slice rather than abstract reference material. Do not assume familiarity with standard framework mechanics (e.g. Spring profiles) — explain the underlying concept even when it is basic for an experienced dev. Confidence: 0.75
- After an explanation, follows up to check whether the mechanic generalizes beyond the case just demonstrated (e.g. asking whether the same Hibernate flush/commit behaviour holds in `@DataJpaTest` *and* the service layer) rather than accepting it as case-specific. Confidence: 0.55
- When something breaks, wants to understand the root cause of their own mistake ("what did I do wrong?") — expects a diagnosis of which mental model was wrong and why it looked half-right, not just the corrected code. Confidence: 0.6
- Works through review findings one at a time — picks a single item from the agent's prioritized list and asks to resolve that one first rather than fixing everything in a batch. Confidence: 0.4
- Bootstraps Java/Spring projects with Spring Initializr (or an IDE wizard) rather than hand-writing build files, then expects the generated project to be verified against the agreed layout and POM coordinates. Confidence: 0.45
- Wants the agent to open each learning task/slice with a heads-up of the specific concepts and new things required to complete it — a short, on-point, comma-separated list (e.g. the annotations, request flow, test types involved), not broad topic areas or generic references. Will also prompt for this concepts list explicitly at the start of a slice if it wasn't given. Confidence: 0.85
- Once the concepts are covered, expects the agent to hand back a concrete, ordered implementation recipe — the exact artifacts to create and the sequence to create them in (e.g. request/response records, service, controller, then the tests) — rather than a scope description, asking directly "what do you want me to do?". Confidence: 0.4
- Encodes recurring workflow expectations as standing rules in the project's `AGENTS.md` (and records them as decisions in the docs) rather than repeating them per task. Confidence: 0.55
- Uses SonarQube/SonarLint static analysis while coding and forwards its findings (e.g. `java:S1068`) to the agent as work items, so linter warnings should be taken seriously and checked against the code. Confidence: 0.4
- Maintains a top-level README documenting the exact command sequence to run the project (bring up Postgres via `docker compose`, activate the profile, run the app) and the test command, and wants those commands confirmed against the real repo layout (correct working directory, correct wrapper invocation) — while keeping secrets out of it, with credentials living in a gitignored local properties file. Confidence: 0.5
- Works in short review/verify cycles: prompts the agent to review or verify at intermediate checkpoints ("can you review now", "can you verify now") rather than waiting for a phase or slice to be finished, and after a round of fixes expects the agent to prove the state by actually executing the build/test suite (running `mvnw -B test`, checking the Docker daemon, etc.) rather than only re-reading the code — findings should be grounded in real command output. Confidence: 0.65
- Asks targeted confirmation questions before committing to an action or accepting an explanation ("should I add X here?", "confirm if `docker compose up` is the command", "so you are saying …?"), so replies should give an explicit yes/no on the proposed plan or understanding and correct it if wrong rather than just moving on. Confidence: 0.65
- States its own mental model of a concept for grading (e.g. writing out answers to the phase review questions such as why both Java validation and DB constraints are needed, or when a write commits) and expects the agent to confirm what is right and pinpoint the specific framing that is wrong, not merely accept or restate it. Confidence: 0.65
